# Drowse WebMCP

Drowse exposes its existing application actions to visiting browser agents. The Python dashboard and hosted browser runtime share tools but retain their actual capability differences. Model weights, inference kernels and token processing do not depend on this layer.

The adapter uses the experimental `document.modelContext.registerTool(tool, {signal})` API. Registration lifetime and invocation cancellation use different signals. Unsupported browsers start the normal UI. This follows the [September 10 specification](https://webmachinelearning.github.io/webmcp/) and [Chrome imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api), checked September 12, 2026. Browser enablement/origin-trial availability is separate from an application's implementation; see [Chrome availability](https://developer.chrome.com/docs/ai/webmcp).

## Discovery and execution

Start with `drowse_get_state`, `drowse_list_actions`, and `drowse_explain_control`. Select a task group with `drowse_select_tool_group`, then discover its typed tools again. State, navigation and the complete action catalogue remain available regardless of the open drawer. `drowse_list_actions({action: "drowse_set_steering"})` returns the input schema, applicability, shared interface/runtime mapping and result contract. `catalogue: true` returns the executable coverage inventory.

Publishing the entire catalogue simultaneously caused the current Codex browser to disable WebMCP because the configuration exceeded its supported limits. Bounded task groups resolved this in a real Codex browser smoke test. This is a consumer constraint observed during integration, not a limit asserted by the WebMCP specification. The native regression lane keeps each group at no more than 32 tools. Selecting a group does not navigate or change model settings.

Tools return plain JSON snapshots: `{ok, data, revision}` or `{ok:false, error:{code,message,details}}`. Large results return a `result_id` for `drowse_read_result`; reconstruct JSON from successive text chunks. Result handles expire with the page. Export tools offer normal downloadable files; an offered download is not proof that the browser saved it to disk. API-key entry uses the existing UI without returning credentials.

Mutation tools accept `expected_revision` to reject stale workspace edits and `request_id` to reconcile an uncertain invocation without repeating it. Revisions include human composer, raw-buffer, form and metadata edits. Saved-chat mutations also accept `expected_metadata_version`, checked inside the shared storage transaction. Reuse a request ID only with identical inputs. An uncertain mutation is never silently replayed.

For long work, retain the job ID and call `drowse_get_job` until a terminal state. A queued receipt or partially generated sibling is not completion. Cancelling an invocation or a status read does not cancel its admitted job; use `drowse_cancel_job`. Authoring, fitting and scoring share UI progress/cancellation where supported. Preparation jobs track their backend family, operation and start identity; cancellation rejects a replacement operation.

Compact job records and mutation receipts survive reloads in the same tab using `sessionStorage`. They expire when the tab closes and have bounded retention; storage-policy/quota failures are exposed in state. Large token/readout payloads are omitted from persisted previews with explicit omission paths. Use affected conversation/artifact IDs to retrieve full details. `drowse_reconcile_job` checks authoritative runtime receipts for interrupted generations and HTTP long operations without repeating computation. Python receipts are process-local and bounded; a server restart or expired receipt leaves an unknown outcome rather than inferred success. Partial comparison results remain available. New comparisons carry a separate system prompt per request and never temporarily change the global prompt; recovery also handles cleanup of earlier interrupted comparisons when that cleanup is still owned.

The `files` group supports chunked binary transfer: begin with a declared size and optional SHA-256, write base64 chunks at exact byte offsets, and finish to validate the file. Pass its `file_id` to a supported chat-backup, background-image or hosted `.drowse` import. Uploading alone changes none of those resources. File handles remain page-local, with a 1 GiB aggregate budget; each import retains its existing format and size restrictions. Identical chunk retries are accepted and conflicting bytes are rejected. Exported archive handles support chunk reads or normal downloads.

## Choosing controls

For “speak like a pirate,” read the current chat instructions, preserve their content, append a concise style instruction using `drowse_set_system_prompt`, and request a sample with `drowse_start_generation`. Inspect the result. This saves a configuration, not a trained model.

For explicit activation steering, search installed controls and node labels first. Inspect the selected artifact's fitted model, variant and geometry before constructing an expression. If the user needs a new generated contrast, use pirate versus assistant with concrete framing and `role_per_node:false`, then fit the artifact. `drowse_compare_generations` accepts labeled conditions with steering, system-prompt and sampling/role overrides. It freezes the parent, model and resolved inputs at admission, generates matched branches, and retains each completed branch if a later condition fails. Change one intervention per branch for attribution. Values 0.25 and 0.5 are exploratory starting points, not calibrated recommendations; reduce them when output repeats or loses meaning.

`drowse_set_role_labels` changes supported template headers. `drowse_update_chat` changes saved-chat metadata. Cast notes are metadata; cast steering takes an expression. The current composer supplies explicit rack steering and thinking, overriding those standing cast defaults. Empty steering explicitly unsteers. A custom expression overrides the visual rack. Role-bearing artifacts may override the requested assistant header. Generation jobs preserve requested settings separately from finalized node recipes, applied steering and role labels.

Base models require the raw workflow: use a textual continuation scaffold, `drowse_set_raw_buffer`, and `drowse_raw_continue`. Raw completion bypasses system instructions and chat-role headers. Raw editing, committing without generation, selections, recompletion and reverting use the mounted editor controller.

The control reference and UI help share `parameterHelp.ts`; `controls.ts` adds applicability, current values, model/session defaults, ranges, units, persistence and interactions. Sampling temperature/top-p/top-k change token selection. They are not persona or factual-quality controls. Sampling top-k and captured-alternative `return_top_k` are distinct. Seeds support comparisons within a fixed environment rather than cross-device guarantees. Probe coordinates, distances, fractions, membership, assignment probabilities, lens probabilities and SAE strengths retain separate units. Probe gates use preceding available readings.

## Integration boundaries

- `lib/webmcp/adapter.ts`: native registration, schema validation, revision checks, idempotency and bounded output.
- `lib/webmcp/index.ts`: page/workspace lifetimes and group discovery. Registrations change with model/capability identity, not token or slider updates.
- `workspaceTools.ts`, `workspaceController.ts`, `homeTools.ts`, `uiTools.ts`: shared UI actions, actual drafts/selections, navigation, saved libraries, appearance, role/cast configuration and diagnostics. The interface group controls visible Loom search/filter/sort/pin/camera, token cursor and replay recipe, and analysis displays. The authoring group reads/edits mounted form drafts through validated shared controllers.
- `serviceTools.ts`: typed adapters to the seven runtime service families. `catalogue.ts` exhaustively classifies all 25 drawers and all 66 runtime methods; interface families include public pages, onboarding and lifecycle controls.
- `generation.ts`, `generationReceipt.ts`, `jobs.ts`, `requests.ts`: frozen queue admission, sibling/comparison completion, durable tab-local receipts, cancellation and interruption. Optional WebSocket `request_id`, per-request `system_prompt` and `request_complete` messages preserve existing uncorrelated clients on both transports. Finalized recipes retain prompt provenance for replay.
- `files.ts`: validated chunk transfers and downloadable artifacts. `server/request_ledger.py` and `server/operation_ledger.py`: bounded authoritative generation and HTTP long-operation receipts, outside per-token processing.
- `publicTools.ts`, `hostedTools.ts`, `lifecycle.ts`: contact drafts/delivery, route/update handoffs, model and pack downloads, storage and tab ownership.

Browser lens fitting and SAE training remain unavailable. Compatible packs use verified download, reload where required and activation. HTTP archive methods remain unsupported. Native server session creation/deletion are not advertised as model switching/session deletion. Surface geometry and authoring parameters follow runtime limits. CLI-only corpus seed arguments are rejected rather than silently ignored.

The layer retains same-origin browser exposure and existing HTTP authentication. Tool definitions contain static application descriptions, never prompt/artifact prose. User/model/artifact results are annotated as untrusted. Credential values are omitted. Existing destructive-action confirmations and explicit contact sending remain in place; contact retry identity is owned by the existing contact store. No prompt/transcript telemetry is added. See [Chrome security guidance](https://developer.chrome.com/docs/ai/webmcp/secure-tools) and [reliability guidance](https://developer.chrome.com/docs/ai/webmcp/best-practices).

## Verification

`npm run test:webmcp` runs adapter, schema, queue, lifecycle, capability, service, workspace, home, hosted/public, file-transfer and visible-interface contracts. Catalogue tests reject unclassified drawers/runtime methods and unknown callable names. Service action cases exercise valid dispatch, invalid inputs, unavailable capabilities and completion for every typed service action. Tests cover stale human edits, unsaved forms, metadata concurrency, role/cast distinctions, empty steering, missing prerequisites, frozen inputs, unrelated errors, sibling finalization, scoped cancellation, interrupted work and reload persistence. Binary tests include a real 65 MiB transfer. Python tests exercise socket disconnection, authoritative completion and long operations that outlive the SSE connection.

`npm run test:webmcp:native` uses pinned Puppeteer 25.10.0 and its Chrome 152.0.7977.75 with `--enable-features=WebMCP`. It starts an isolated fixture site and exercises the native `page.webmcp` API, all task groups, schema registration, actual visible controls, generation receipts, model onboarding and route cleanup. A second launch disables WebMCP and verifies ordinary startup. The lane is configured in CI and has passed locally; it is not mock registration. [Puppeteer WebMCP documentation](https://pptr.dev/guides/webmcp).

The real Codex in-app browser separately discovered and invoked guidance, instruction, visible-interface and binary-transfer tools. This caught an uncloneable reactive-result bug, now fixed by JSON snapshot conversion and covered in both adapter and native tests. Fixture generation is deterministic interface evidence, not a behavioral evaluation of a language model.

Real native model integration can be reproduced with `scripts/webmcp-live-server.py` plus `scripts/webmcp-live-http.mjs`, using isolated model/cache directories. The shared live scenario runs prompting/role/steering comparisons, sampling changes, save/rename, missing-artifact lookup, owned cancellation and disconnect/reload recovery. Base models exercise raw continuation separately. `DROWSE_WEBMCP_NATIVE_EVIDENCE=1` adds this scenario to the existing real production WebGPU application harness. It preserves that harness's model/artifact/runtime verification; no successful release evidence is inferred from fixture tests.

Local native Python chat and base runs passed on CPU/fp32. The chat comparison verifies the effective prompt stored on each generated branch. Network loss followed by reload reconciles the cancelled backend operation without another generation. The base continuation records that chat instructions were bypassed; its pirate scaffold produced pirate language with repetition. These outcomes are specific to the small models and prompts tested. Dated local evidence is retained privately; the reproducible scripts ship with the source.

Reproduce the separate small-model behavior experiment with `scripts/webmcp-model-evidence.py`. SmolLM2-135M-Instruct and its base model ran in isolated caches on MPS/fp32, with seed 1729 and a 40-token ceiling. In the tested prompt, system instructions and role substitution changed output but did not reliably produce pirate language. A fitted pirate intervention at 0.25 and 0.5 collapsed into punctuation repetition; lower 0.01/0.05 coefficients were fluent without clear pirate style. Raw runs kept identical token arrays when only system/role settings changed, while a raw scaffold changed the continuation. These observations support the distinct control semantics and the need to inspect quality; they do not establish a universally effective pirate recipe.
